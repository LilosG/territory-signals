# Architecture

## Layers
| Layer | Purpose | Folder | Tables |
|---|---|---|---|
| Collect | Pull raw data from sources and owner providers | `pipelines/territory/sources/`, `owner_data/` | `source_runs`, `raw_records` |
| Connect | Match records to parcels and normalize into signals | `pipelines/` | `parcels`, `neighborhoods`, `signals`, `owners`, `sales_history` |
| Score | Deterministic scoring and recipe matching | `pipelines/` | `scores`, `suppressions` |
| Act | Draft outreach for human approval; record outcomes | `pipelines/` | `outreach`, `outcomes`, `team_members` |
| Explain (AI) | Provider-agnostic text layer: classify permit text, write lead and weekly briefs. Validated, shadow-labeled, never scores | `pipelines/territory/llm/` | `ai_outputs`, `ai_task_runs` |
| Show | Dashboard (Astro + Tailwind) | `dashboard/` (Phase 4) | reads all via RLS |

## Data flow
Source adapter `fetch` -> `raw_records` (append-only, tied to a `source_runs` row) -> `normalize` -> `SignalCandidate` -> match to a parcel (apn, spatial, address or name) -> `signals` (append-only) -> scoring reads `signals` + `owners` + `sales_history` -> `scores` -> outreach drafts in `outreach` (status flow draft -> awaiting_approval -> approved -> sent) -> `outcomes` recorded by team members. Per-client settings come from `config/clients/<client_id>.yaml`.

## Table reference
All tables are in `public`, have a `created_at timestamptz default now()`, have RLS enabled (authenticated users select; writes only via the service role). Primary keys are uuid unless noted.

- **neighborhoods**: id, name, planning_area, geom MultiPolygon(4326), is_official
- **parcels**: apn (text PK), situs_address, zip, planning_area, neighborhood, geom MultiPolygon(4326), centroid Point(4326), lot_sqft, land_use, zoning, year_built, last_recorded_doc_date, source_key, updated_at
- **source_runs**: id, source_key, started_at, finished_at, status (running|success|failed), rows_fetched, rows_matched, rows_unmatched, error_message
- **raw_records**: id, source_key, source_record_id, run_id -> source_runs, payload jsonb, fetched_at; unique(source_key, source_record_id, fetched_at)
- **signals**: id, apn -> parcels, signal_type, signal_group, signal_date, detected_at, source_key, source_record_id, run_id -> source_runs, confidence (0..1), match_method (apn|spatial|address|name), is_estimate, is_sample, details jsonb
- **owners**: id, apn -> parcels, owner_name, mailing_address, owner_occupied, absentee, out_of_state, last_sale_date, last_sale_price, mortgage_open, est_value, est_equity, provider (attom|sample), is_sample, as_of; a new row per as_of, never updated in place
- **sales_history**: id, apn -> parcels, sale_date, sale_price, doc_type, provider, is_sample
- **scores**: id, apn -> parcels, score (0..100), components jsonb, reason_text, recipe_matches text[], model_version, scored_at
- **suppressions**: id, apn -> parcels, reason, until_date
- **outreach**: id, apn -> parcels, channel (mail|email|call_task), status (draft|awaiting_approval|approved|sent|suppressed), content, source_facts jsonb, approved_by, sent_at; Phase 5A adds recipe, assigned_to, due_date, mailing_address, salutation, template_key, model_version, blocked_reason, uses_sample_data. A check constraint stops a row with a `blocked_reason` from becoming approved or sent (D11)
- **outcomes**: id, apn -> parcels, team_member_email, status (contacted|conversation|appointment|listing|not_interested|bad_data), noted_at, note
- **team_members**: id, email (unique), name, role (owner|agent|assistant)
- **stage_events** (Phase 5A, append-only): id, apn -> parcels, stage (signal|contacted|conversation|appointment|listing|not_interested|bad_data), team_member_email, occurred_at, note, source (dashboard|system)
- **Views** (security_invoker): `latest_scores`; `funnel_by_recipe` and `funnel_by_agent` count distinct parcels per stage from `stage_events` joined to `latest_scores` (`funnel_by_recipe` counts each parcel once under `scores.primary_recipe`, the matched recipe whose components contribute the most points; events with no agent show as `unassigned`)

Indexes: GIST on `neighborhoods.geom`, `parcels.geom`, `parcels.centroid`; btree on `signals(apn, signal_type, signal_date)`, `scores(scored_at)`, `outreach(status)`.

## Adapter interfaces
- `SourceAdapter` (`sources/base.py`): `source_key`; `fetch(run_id) -> Iterable[RawRecord]`; `normalize(raw) -> Iterable[SignalCandidate]`.
- `OwnerDataProvider` (`owner_data/base.py`): `get_owner(apn)`, `get_sales_history(apn)`, `bulk_owners(apns)`. Implementations: `SampleOwnerProvider` (deterministic, `is_sample=True`, owner_name "Sample Owner <last 4 of APN>") and `AttomOwnerProvider` (skeleton; raises `NotConfiguredError` without `ATTOM_API_KEY`).

## Scoring (Phase 3)
Deterministic only: no AI, no randomness (CLAUDE.md AI rules). Config: `config/scoring.yaml` (`model_version` v0.4.1-handset). Code: `territory/scoring_engine.py` (pure functions), `territory/score.py` (database + CLI), `territory/permit_rules.py` and `territory/permit_rederive.py` (permit groups and the stalled rule), `territory/owner_data/load.py` (owner layer).

Steps, in order: `python -m territory.run ...` (collect) -> `python -m territory.permit_rederive --client <id>` -> `python -m territory.owner_data.load --client <id>` -> `python -m territory.score --client <id>`. Run from `pipelines/`. Every command refuses a non-local database host unless `--cloud` is passed (D16).

- **Residential filter.** Only parcels whose `land_use` is listed under `residential_land_use` in scoring.yaml are scored. The distinct codes are profiled in `pipelines/territory/sources/reports/land_use_profile.csv` (`--profile-land-use`).
- **Suppression.** No score for a parcel with a `sales_history` sale in the last 24 months, or an active `suppressions` row (`until_date` null or not yet passed).
- **Live signals.** A signal is live when `superseded_by is null`. `superseded_by` (new in Phase 3) holds the id of the `permit_rederive` run that superseded the row; replacement rows carry that run id. Signals stay append-only: the only UPDATE the database allows is `superseded_by` going from null to a run id.
- **Components.** One component per signal key (signal type; permits also by group): the most recent live instance. `contribution = weight x 0.5 ** (age_days / half_life_days) x confidence` (the signal's match confidence, recorded as `confidence_multiplier`); static signals do not decay. `tax_default` decays from the date of the notice/list the parcel appears on (`signal_date`); the original default date stays in details and the reason text. Snapshot signals (`stro_license_active`, `sb9_lot_split_estimate`, `sb79_transit_estimate`, `fire_hazard_zone`) count only if the parcel has a row dated on the latest snapshot date for that type, so repeated daily rows never stack. Owner modifiers come from the latest `owners` row (years owned, out of state otherwise absentee, no open mortgage, est. equity at or above the territory 75th percentile). Out of state (+12) and absentee (+10) are not additive, and the total owner-modifier contribution is capped at 30 (over the cap every owner component is scaled by the same `cap_multiplier`).
- **Score.** `min(100, round_half_up(sum(contributions) x stacking))`, stacking = 1 + 10% per signal family beyond the first (financial, rental, permits, upzoning, fire, owner), capped at +30%. A family counts when one of its components has a positive contribution. 
- **scores row.** One row per scored parcel per run (`scored_at` is shared by a run; the table is append-only). `components` is a JSON list; each item has `key`, `family`, `signal_id` or `owner_field`, `raw_weight`, `decay_factor`, `contribution`, `is_sample`, `is_estimate`, source fields (`source_key`, `source_record_id`, `confidence`, `match_method`) and the `facts` the reason text may use. `uses_sample_data` is true when any component is sample-derived. Readers use the `latest_scores` view (most recent row per parcel, `security_invoker` so RLS on `scores` applies).
- **Recipes.** Declarative conditions over the parcel's effective signals and owner fields (`all`/`any`/`not`, signal presence with optional group, `within_days` and detail filters, owner comparisons). `builder_bait` needs an upzoning estimate, `lot_sqft` at least 1.5x the median residential `lot_sqft` of the parcel's planning area (medians are written to `sources/reports/scoring_report.md`) and 20+ years owned. `insurance_squeeze` is active only when fire-zone signals exist; `quiet_inheritance` is `active: false` (requires ATTOM recorder data, Phase 6).
- **reason_text.** Built from the top components only (max 4, by contribution), using only the component `facts`. Permits are shown by the plain-English label in `config/permit_labels.yaml`, never the raw type (a type with no label fails scoring). Sample-derived facts end with "(sample data)", estimates with "(estimated)".
- **Permit groups.** `config/permit_signal_map.yaml` (status reviewed) maps `APPROVAL_TYPE` to group; `APPROVAL_ADU_TOTAL > 0` regroups a permit as `adu`. The discretionary types under `residential_remodel_types` (coastal, site development, use permits, variances, ...) become remodel_addition when the record is residential (parcel land use, or the record's own PROJECT_TYPE/APPROVAL_TYPE). `permit_stalled` counts only for remodel_addition, adu and demolition_lot_split, and only when the permit expired more than 90 days and at most 36 months ago with no close date. The signal natural key includes `signal_group` and `superseded_by`, so a regrouped signal is a new row and a group an approval once had can be live again.


## Phase 5A: data rules, catalog, outreach drafts
Run from `pipelines/`: `python -m territory.export_catalog` (names), `python -m territory.score --client <id>` (re-score), `python -m territory.outreach --client <id> [--channels mail,email,call_task] [--drafts N] [--dry-run]`.

- **Single source of truth for names.** `territory.export_catalog` writes `dashboard/src/data/catalog.generated.json` from `config/scoring.yaml` (recipe labels, short descriptions, score bands), `config/permit_labels.yaml`, `config/signal_labels.yaml` (signal types, groups, score components, families, stages) and the client's recipe toggles (`enabled`). Sentence case, acronyms kept. A test fails if the committed file is stale or a score component has no label. The dashboard reads only this file (Phase 5B).
- **Ownership rule.** `config/transfer_types.yaml` lists the doc types that are a transfer by death, trust or inheritance. If the latest `sales_history` record is one (and the `owners` row shows no later sale), `resolve_tenure` makes the transfer date the current owner's tenure start. The earlier tenure is stored as `prior_owner_years` on a zero-point `owner:ownership_transfer` component and never printed as the current owner's tenure. Each transfer is also recorded as an `ownership_transfer` signal (group `life_event`; never scored) and never triggers the 24-month sale suppression. `SampleOwnerProvider` ends about one parcel in ten with such a transfer and always sets `last_sale_date` to it. The owner loader now appends a corrected `owners` row when the content for the same `as_of` changed (identical rows are still skipped); readers take the newest.
- **reason_text (v0.3).** A phrase is never repeated; same-day permits of one kind merge ("2 building permits ... approved Nov 16, 2026"); a tier prints once ("Tier 3 short-term rental license"); a fact that is both sample and estimated reads "(sample data, estimated)"; years are whole numbers.
- **Outreach drafts (D10, D11).** `territory/outreach.py` takes the top `drafts_per_run` parcels from the latest scoring run that match an enabled recipe, are not suppressed (active `suppressions` row or a sale inside the suppression window) and have no outreach row inside `cooldown_days`. The primary recipe is the enabled matched recipe whose referenced components contribute the most points (ties: config order). Templates: `config/outreach_templates/<recipe>/{letter,email,call_script}.md` (front matter `facts:` names the component keys a text relies on; `general/` is the fallback), rendered by `territory/outreach_render.py`. Salutations come from `territory/salutation.py` (LAST FIRST names, trusts, couples, trustees; anything unreadable, an organization, an estate or a sample name becomes "To the owners of <situs address>,"). Rows are `draft`, or `awaiting_approval` for `approval_required_recipes`; `source_facts` holds exactly the component facts the template relies on plus the owner name when the greeting uses it; `blocked_reason` is "missing agent name or DRE license" (D11) and, for email, "missing office address". Homeowner text never contains labels such as "(estimated)", "(sample data)", signal names or scores (tests enforce this); drafts built on sample data set `uses_sample_data` and get `blocked_reason` "sample data". Templates are short (letter 70-130 words, email 50-100, call script under 90): local focus, why now, one offer per recipe, one call to action. `source_facts` also lists the neighborhood and street (parcel fields) the text uses. Agents are assigned round-robin over `team_members` with role `agent` (sorted by email; null when there are none). Mode `preview` only writes rows: no sending, no network, no AI.


## Dashboard (Phase 5B)
Astro 7, server output (`@astrojs/cloudflare`, hosted on Cloudflare Workers; see `DEPLOY.md`), Tailwind 4, MapLibre 6, ECharts 6. Run notes are in `dashboard/README.md`.

- **Names.** `src/lib/data/catalog.ts` reads only `src/data/catalog.generated.json` (signals, groups, permit types, recipes, components with max points, score bands, stages, model_version). The only hand-written lists are external source links and outreach status labels. Fixtures and live data share that vocabulary (`scripts/generate-fixtures.ts`).
- **Data layer.** `DataProvider` (`lib/data/provider.ts`) has two implementations selected by `DATA_PROVIDER` (default `supabase`): `supabase.ts` (user session via `@supabase/ssr`; RLS applies) and `fixtures.ts`. Providers call `mark()` whenever data shown is sample (`uses_sample_data` / `is_sample`); `AppShell` shows the sample banner from that on every page.
- **Reads.** Views `latest_scores`, `latest_owners` (max `as_of`), `funnel_by_recipe`, `funnel_by_agent`, `funnel_overall`, `trend_turnover_monthly`, `trend_signals_monthly`, `trend_upzoning_by_hood`, `trend_recipes_by_hood`; functions `leads_page(...)` (filters, paging, total) and `map_points(...)` (compact rows for `/api/map`, which returns GeoJSON). Signals are read with `superseded_by is null`.
- **Auth.** Supabase Auth email magic link (PKCE; `/login`, `/auth/callback`). A `before insert` trigger on `auth.users` refuses emails not in `team_members`; RLS on every table requires `is_team_member()`. `middleware.ts` redirects everything except `/login`, `/auth/*` and `/share/*`. `territory.seed_team` fills `team_members`.
- **Actions** (SECURITY DEFINER, each checks the caller is on the team; plain form POSTs to `/actions/*`): `edit_outreach`, `approve_outreach` (refuses a draft with `blocked_reason`; mode stays preview, nothing is sent), `record_stage` (also writes the parcel's `signal` entry once), `create_share_link`, `revoke_share_link`. New columns on `outreach`: `original_content`, `edited_by`, `edited_at`. New table `share_links`.
- **Share page.** `/share/[token]` calls `share_page(token)` (anon-executable), which returns neighborhood, lot size, zoning, year built, estimated upzoning types and the agent (name, email; phone from config) and nothing else.

## Dashboard (Phase 5D: product depth)
- **Reads.** Migration `20261120000000_dashboard_5d.sql` adds the materialized view `private.scored_parcels` (one row per scored, unsuppressed parcel: latest score, parcel facts, recipe matches, latest selling event date; refreshed by `private.refresh_dashboard_aggregates()`), exposed through the `security_invoker` view `scored_parcels`, plus views `outreach_queue`, `share_links_active`, `source_latest` and functions `nav_counts`, `leads_list`, `recipe_summary`, `recipe_top_leads`, `off_market_inventory`, `search_leads`, `today_stats`, `recent_signals`, `funnel_by`, `coverage_weekly`. All take an optional neighborhood (the territory) and are executable by `authenticated` only; the functions are `security invoker` with no `SET search_path` so Postgres can inline them. Timings as a team member are all under 100 ms locally (`tests/test_dashboard_timing.py`, limit 500 ms).
- **Territory.** The sidebar switcher posts to `/actions/territory`, which sets the `ts_territory` cookie (validated against the client config). `middleware.ts` puts it in `locals.territory`; every page, `/api/leads`, `/api/map` and `/api/search` read it.
- **Pages.** Work: Today, Leads (saved views, sort, filters), Outreach (tabs with counts, bulk approve), Pipeline. Opportunities: Map (30+ by default), Recipes, Off-market (bulk share links). Market: Trends, Reports (newsletter and printable neighborhood reports). Results: Performance (funnels, backtest empty state, coverage). Admin: Data sources, Team, Settings.
- **Bulk actions.** `/actions/approve-bulk` and `/actions/share-bulk` (capped at 50) call the same `approve_outreach` and `create_share_link` functions one item at a time, so every database rule still applies; blocked drafts are skipped and named.
- **Presentation rules** live in `lib/present.ts` and `data/landUse.ts`: no distress or life-event chips on cards or lists (only in the brief's "Sensitive records" card), one sample badge per card, sample facts dotted-underlined, estimates tagged "est.", land use labels, same-day permits collapsed, the "other" permit group never shown.
- **Tests.** Playwright (`npm run e2e`) covers the sign-in flows, Today, navigation, the Outreach bulk approve with a blocked draft, Recipes links, Off-market share link with no owner data, the territory switcher, Cmd+K search and every page. Its setup seeds two synthetic parcels and refreshes the materialized view; teardown removes them and refreshes again.


## AI layer (Phase 5F)
```
facts (SQL / DB rows only) -> packet (records R1..Rn: source, date, confidence, is_sample, is_estimate)
   -> cache check (input_hash + prompt_version) -> budget guard -> provider.complete(json_schema)
   -> parse + deterministic validators -> retry once with the reason appended -> fallback model -> ai_outputs (one row per attempt, valid | rejected | invalid, append-only)
   -> latest_ai_outputs view -> dashboard ("AI summary" tag, claims link to their records)
```
- **Code.** `llm/base.py` (interface, structured-output wrapper), `openai_compatible.py`, `anthropic_provider.py`, `fake.py`, `factory.py` (provider from the client config; returns "skip" when `llm.enabled` is false or the key env var is missing), `pricing.py`, `prompts.py` (`config/prompts/<task>/v<N>.md`; `prompt_version` is the file name), `store.py` (writes, cache, monthly spend, budget guard), `validators.py`, `tasks/{permit_intent,lead_brief,weekly_brief}.py`, `runner.py`, `eval.py`, `select_models.py`.
- **Tasks.** `permit_intent` (shadow mode; 15 permits per call; one row per permit), `lead_brief` (every parcel with latest score at least 40, plus the top 200; one row per parcel), `weekly_brief` (SQL facts per neighborhood and territory; one row per week, `subject_type = territory`, `subject_id` = the week's first day). Order in `python -m territory.run --client <id> --source all` and `--only-ai`: permit_intent, lead_brief, weekly_brief, after the aggregate refresh. `--skip-ai` leaves them out.
- **Tables.** `ai_outputs` (append-only, RLS like the other tables): id, client_id, task, subject_type (parcel|permit|territory), subject_id, input_hash, prompt_version, provider, model, output jsonb, cited_record_ids text[] (signal ids, `owner:<field>`, `parcel:<apn>`, `score:<id>`, `week:<date>`), uses_sample, status (valid|invalid|rejected), rejection_reason, token counts, cost_usd (null = unknown). `ai_task_runs` (one row per task per run: calls, cached, invalid, rejected, tokens, cost, warnings; read by the Pipeline page). Views: `latest_ai_outputs` (latest valid row per task and subject), `ai_month_spend`.
- **Retry and fallback (Phase 5G, `llm/attempts.py`).** Every task runs a chain per subject: the task's model; on a rejected or invalid reply, the same model once more with the rejection reason appended (an empty reply counts as rejected); then `llm.tasks.<task>.fallback_model`. A provider error skips the retry and goes to the fallback. `permit_intent` retries and falls back only the permits in a batch that failed. Every attempt is stored (`attempt` 1-3, `is_fallback`); `latest_ai_outputs` shows only the latest valid row, so a rejected first attempt is never shown. `ai_task_runs` gains `retried` and `fallbacks`. Fallbacks for Kaiser Team: lead_brief and weekly_brief `qwen/qwen3.6-35b-a3b`, permit_intent `qwen/qwen3.6-27b`.
- **Lead brief v2 and weekly brief v2 (Phase 5G).** The lead brief packet adds citable `meaning` records (what each signal means, `config/signal_labels.yaml` `signal_meanings`) and `pattern` records (each matched recipe's `rationale` in `config/scoring.yaml`); cited as `meaning:<component key>` and `recipe:<key>`. Validators add: numbers may be rounded or abbreviated forms of packet numbers ($3.05M, 26%), at most one header fact (lot size, zoning, permit date, years owned) in the summary, headline at most 10 words with no zoning code, jargon or "Recent permits" opener, no generic market-update angle, no "sample data", "playbook" or "recipe" in prose, and at least one claim citing a record about the home itself. The weekly brief is shown only what is new or changed (`weekly_brief.model_view`), may not say what did not change, and compares only scoring runs of the same model version.
- **Budget guard.** Before each call, the month's `cost_usd` plus the average cost per call so far in the run must stay under `llm.monthly_budget_usd`; otherwise the task stops, the run is `budget_stopped` and a warning appears on the Pipeline page.
- **Dashboard.** Reads `latest_ai_outputs` only when the client config has `llm.enabled: true`. With the layer off (or no rows) nothing AI-related renders. Lead brief (5G): one card holds the AI headline, summary, recipe chips, internal suggested angle and a collapsed "Sources (N)" list (each claim linking to its record on the Signals or Owner tab); with no valid brief the same card shows the deterministic "Why this lead" text and no AI tag; Score components are their own card. Leads and Today: the AI headline is the bold primary line with a sparkle icon, the top signal the small gray line. Today: "This week" card. Reports: Briefings archive (`/reports/briefings`, one page per week). Trends newsletter: the latest newsletter paragraph. Pipeline: per-task row (calls, cached, invalid, rejected, tokens, cost this run, month vs budget).
